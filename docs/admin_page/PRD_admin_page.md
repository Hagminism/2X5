# PRD: 관리자 페이지

## 1. 문서 개요

- 문서명: 관리자 페이지 PRD
- 문서 목적: 관리자(업장 운영자) 기능의 MVP 범위, 사용자 흐름, 권한 정책, 데이터 요구사항을 정의한다.
- 기준 문서:
  - `docs/PRD.md`
  - `docs/admin_page_spec.md`
  - `docs/requirements_specification.md`
  - `docs/project_proposal.md`
  - `docs/convention.md`

---

## 2. 제품 목표

### 2.1 관리자 사용자 목표

- 최소 정보로 계정을 빠르게 생성한다.
- 관리자 페이지에서 사업자 인증과 업장 등록을 단계적으로 진행한다.
- 업장 정보, 예약 자원, 예약 현황을 한 화면 체계에서 관리한다.

### 2.2 운영 목표

- 사업자 검증 상태를 기준으로 관리자 기능 활성화 범위를 제어한다.
- 멀티테넌트 구조에서 관리자 간 데이터 접근을 격리한다.
- 예약 상태 변경이 운영 화면에 실시간으로 반영되도록 유지한다.

---

## 3. 대상 사용자

### 3.1 업장 운영자(관리자)

- 회원가입 후 업장을 등록하고 예약 운영을 수행하는 사용자

### 3.2 플랫폼 관리자

- 사업자 인증 제출 건을 검토하고 승인/반려를 처리하는 사용자

---

## 4. 핵심 정책

### 4.1 가입/인증 분리 정책

- 관리자 회원가입 단계에서는 일반 사용자와 동일한 기본 정보만 입력한다.
- 사업자 정보 입력, 증빙 첨부, 검증/승인 절차는 관리자 페이지 진입 후 수행한다.
- 검증 실패는 회원가입 실패와 분리하여 처리한다.

### 4.2 역할/상태 분리 정책

- 사용자 역할(`role`)과 관리자 검증 상태(`partner_status`)를 분리 관리한다.
- `partner_status`가 `approved`가 아니면 핵심 관리자 기능을 제한한다.

예시 상태:
- `unverified`: 인증 미제출
- `pending`: 제출 후 검토 대기
- `approved`: 승인 완료
- `rejected`: 반려

---

## 5. MVP 범위

### 5.1 MVP 포함

- 관리자 계정 생성(기본 정보 기반)
- 관리자 온보딩 진입
- 사업자 인증 정보 입력
  - 사업자등록번호(10자리 정책)
  - 대표자명
  - 개업일자
  - 사업자등록증 첨부
- 사업자 인증 상태 조회(대기/승인/반려)
- 업장 정보 등록/수정
- 운영 시간 등록/수정
- 예약 자원 등록/수정/활성 관리
- 예약 현황 조회 및 상태 변경
- 쿠폰/스탬프 자동 정산

### 5.2 MVP 제외

- 고도화된 자동 심사 모델
- 외부 예약 플랫폼 실시간 재고 동기화

---

## 6. 기능 요구사항

### 6.1 대시보드

- 오늘 예약 건수, 상태별 건수, 임박 예약 목록을 제공해야 한다.
- 인증 상태 배지(`unverified`, `pending`, `approved`, `rejected`)를 표시해야 한다.
- 주요 작업(인증 제출, 업장 등록, 예약 현황 이동) 바로가기를 제공해야 한다.

### 6.2 사업자 인증

- 인증 입력값:
  - 사업자등록번호
  - 대표자명
  - 개업일자
  - 사업자등록증 파일
- 인증 제출 후 상태를 조회할 수 있어야 한다.
- 반려 시 반려 사유를 확인하고 재제출할 수 있어야 한다.
- 국세청 진위확인 API 결과를 저장/추적할 수 있어야 한다.

### 6.3 업장 관리

- 업장 기본 정보를 등록/수정할 수 있어야 한다.
  - 업장명, 업종, 주소, 연락처
  - 위도/경도, 외부 장소 식별자
- 운영 시간을 등록/수정할 수 있어야 한다.
- 운영시간 입력 시 역전 시간(오픈 > 마감)을 방지해야 한다.

### 6.4 예약 자원 관리

- 업장별 예약 자원을 등록/수정할 수 있어야 한다.
- 자원별 수용 인원, 슬롯 길이, 상태(활성/비활성)를 관리할 수 있어야 한다.

### 6.5 예약 현황

- 날짜/상태/자원 기준으로 예약을 조회할 수 있어야 한다.
- 예약 상세 정보와 상태 이력을 확인할 수 있어야 한다.
- 예약 상태(확정/취소/완료)를 변경할 수 있어야 한다.

### 6.6 접근 제어

- 관리자는 본인 업장(`owner_id`) 데이터만 조회/수정할 수 있어야 한다.
- 승인 전(`approved` 이전)에는 업장 공개/예약 수신 같은 핵심 기능을 제한해야 한다.

### 6.7 쿠폰/스탬프 관리

- 관리자는 업장별 쿠폰/스탬프 정책을 생성/수정할 수 있어야 한다.
  - 예: `10회 적립 시 1회 무료`, `예약 완료 시 1스탬프 적립`
- 예약 완료/이용 완료 이벤트를 기준으로 자동 적립이 수행되어야 한다.
- 사용자가 쿠폰을 사용하면 차감 이력이 기록되어야 한다.
- 예약 취소/환불 등 정산 취소 조건에서 적립/차감 롤백 규칙이 적용되어야 한다.
- 같은 이벤트의 중복 처리로 인한 중복 적립이 발생하지 않아야 한다.

## 7. 데이터 요구사항

### 7.1 stores 테이블 매핑

- 주요 컬럼:
  - `id`
  - `owner_id`
  - `name`
  - `category`
  - `business_number`
  - `address`
  - `latitude`
  - `longitude`
  - `naver_place_id`
  - `contact`
  - `operating_hours`
  - `created_at`

### 7.2 후속 도메인 테이블

- `owner_verifications`
  - `owner_id`, `store_id`
  - `representative_name`, `opened_on`, `business_number`
  - `license_file_url`
  - `nts_validation_result`, `nts_validated_at`
  - `status`, `rejection_reason`, `submitted_at`, `reviewed_at`
- `resources`
  - `store_id`, `name`, `resource_type`
  - `min_capacity`, `max_capacity`, `slot_minutes`, `is_active`
- `reservations`
  - `store_id`, `resource_id`, `user_id`
  - `date`, `start_time`, `end_time`, `party_size`
  - `status`, `request_note`, `created_at`
- `coupon_policies`
  - `id`, `store_id`, `name`, `rule_type`
  - `stamp_goal`, `reward_type`, `reward_value`, `is_active`
- `user_coupon_wallets`
  - `id`, `user_id`, `store_id`, `policy_id`
  - `current_stamps`, `issued_coupons`, `used_coupons`, `updated_at`
- `coupon_ledger`
  - `id`, `user_id`, `store_id`, `policy_id`, `reservation_id`
  - `event_type` (`earn`, `use`, `rollback`)
  - `amount`, `idempotency_key`, `created_at`

### 7.3 무결성 권장사항

- `owner_id` 타입은 인증 사용자 PK 타입과 일치시킨다.
- `business_number`에 `UNIQUE` 제약을 적용한다.
- `latitude`, `longitude`는 동시 존재 또는 동시 NULL 규칙을 적용한다.
- `operating_hours` JSON 구조/시간 포맷을 검증한다.

## 8. 핵심 사용자 시나리오

### 8.1 관리자 신규 진입

1. 관리자가 기본 정보로 회원가입한다.
2. 로그인 후 관리자 온보딩으로 이동한다.
3. 사업자 인증 정보를 입력하고 제출한다.
4. 검토 대기 상태를 확인한다.
5. 승인 후 업장 등록 및 예약 운영 기능을 사용한다.

### 8.2 예약 운영

1. 관리자가 자원을 등록한다.
2. 사용자가 예약을 생성한다.
3. 관리자는 예약 현황에서 신규 예약을 확인한다.
4. 필요 시 상태를 변경하고 운영에 반영한다.

### 8.3 쿠폰/스탬프 자동 정산

1. 관리자가 업장 쿠폰/스탬프 정책을 설정한다.
2. 사용자가 예약을 완료(또는 이용 완료)한다.
3. 시스템이 정책에 따라 스탬프를 자동 적립한다.
4. 목표 적립 조건 충족 시 쿠폰이 자동 발급된다.
5. 사용자가 쿠폰을 사용하면 차감 이력이 기록된다.
6. 취소/환불 시 정책에 따라 적립/사용 이력이 롤백된다.

## 9. 비기능 요구사항

### 9.1 데이터 정합성

- 동일 시간대 동일 자원 중복 배정을 방지해야 한다.
- 예약 상태 전이 규칙을 강제해야 한다.
- 쿠폰/스탬프 정산은 이벤트 중복 처리에도 단 한 번만 반영되어야 한다.

### 9.2 멀티테넌트 보안

- 테넌트 스코프 누락으로 인한 교차 접근이 없어야 한다.
- 관리자 간 데이터 접근 격리를 테스트 케이스로 검증해야 한다.

### 9.3 실시간성

- 예약 생성/변경/취소 이벤트가 관리자 화면에 지연 없이 반영되어야 한다.
- 동시성 충돌 시 사용자/관리자 화면 최종 상태가 일치해야 한다.

### 9.4 운영 추적성

- 인증, 예약, 접근 거부 이벤트를 추적할 수 있어야 한다.
- 장애 분석을 위한 핵심 이벤트 로그를 확보해야 한다.
- 적립/사용/롤백 정산 이벤트를 감사 로그로 추적할 수 있어야 한다.
